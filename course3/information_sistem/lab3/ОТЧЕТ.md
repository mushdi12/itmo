## 1. Подключение к базе данных через Connection Pool (Druid)

### 1.1. Теоретическая часть

#### Что такое Connection Pool?

**Connection Pool (пул соединений)** — это механизм управления соединениями с базой данных, который позволяет переиспользовать уже установленные соединения вместо создания новых для каждого запроса.

#### Преимущества использования Connection Pool:

1. **Производительность**: Избежание накладных расходов на установку соединения
2. **Управление ресурсами**: Ограничение количества одновременных соединений
3. **Мониторинг**: Отслеживание использования соединений
4. **Надежность**: Валидация и восстановление соединений

#### Почему выбран Druid?

**Druid** — это высокопроизводительный пул соединений для Java, разработанный Alibaba. Преимущества:

- **Мониторинг в реальном времени**: Статистика SQL, медленные запросы
- **Защита от SQL-инъекций**: Встроенный фильтр `wall`
- **Производительность**: Оптимизирован для высоконагруженных систем
- **Гибкая конфигурация**: Множество параметров настройки

### 1.2. Реализация

#### 1.2.1. Добавление зависимости

В файле `pom.xml` добавлена зависимость:

```xml
<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>druid</artifactId>
    <version>1.2.20</version>
</dependency>
```

#### 1.2.2. Создание DataSource Provider

Создан класс `DruidDataSourceProvider`, который инициализирует пул соединений:

```java
@ApplicationScoped
public class DruidDataSourceProvider {
    private DruidDataSource dataSource;
    
    @PostConstruct
    public void init() {
        dataSource = new DruidDataSource();
        // Настройка подключения и параметров пула
    }
}
```

#### 1.2.3. Конфигурация параметров

Параметры настраиваются в классе `DruidDataSourceProvider` и описаны в файле `druid.properties`.

### 1.3. Параметры конфигурации Druid

| Параметр | Значение | Описание и влияние на производительность |
|----------|---------|------------------------------------------|
| `initialSize` | 5 | **Начальный размер пула** при старте приложения. Уменьшает время первого запроса, так как соединения уже готовы. |
| `minIdle` | 5 | **Минимальное количество простаивающих соединений**. Обеспечивает быстрый отклик при внезапной нагрузке. |
| `maxActive` | 20 | **Максимальное количество активных соединений**. Ограничивает нагрузку на БД и предотвращает исчерпание ресурсов. |
| `maxWait` | 60000 мс | **Максимальное время ожидания** свободного соединения. При превышении выбрасывается исключение. |
| `timeBetweenEvictionRunsMillis` | 60000 мс | **Интервал проверки** простаивающих соединений. Позволяет обнаруживать "мертвые" соединения. |
| `minEvictableIdleTimeMillis` | 300000 мс (5 мин) | **Минимальное время простоя** перед удалением соединения. Освобождает ресурсы неиспользуемых соединений. |
| `validationQuery` | SELECT 1 | **SQL-запрос для валидации** соединения. Проверяет работоспособность перед использованием. |
| `testWhileIdle` | true | **Проверка соединений во время простоя**. Обнаруживает разорванные соединения до их использования. |
| `testOnBorrow` | false | **Проверка при получении**. Отключена для производительности (используется `testWhileIdle`). |
| `testOnReturn` | false | **Проверка при возврате**. Отключена для производительности. |
| `poolPreparedStatements` | true | **Кэширование PreparedStatement**. Улучшает производительность повторяющихся запросов. |
| `maxPoolPreparedStatementPerConnectionSize` | 20 | **Максимум PreparedStatement** на соединение. Ограничивает использование памяти. |
| `filters` | stat,wall | **Фильтры**: `stat` — статистика, `wall` — защита от SQL-инъекций. |

#### 1.3.1. Влияние параметров на производительность

- **`initialSize` и `minIdle`**: Высокие значения уменьшают задержку первого запроса, но увеличивают потребление ресурсов
- **`maxActive`**: Слишком низкое значение приводит к блокировкам, слишком высокое — к перегрузке БД
- **`maxWait`**: Должен быть достаточным для пиковых нагрузок, но не слишком большим
- **`poolPreparedStatements`**: Значительно улучшает производительность при повторяющихся запросах

## 2. Добавление L2 JPA Cache (Infinispan)

### 2.1. Теоретическая часть

#### Что такое L2 Cache (кэш второго уровня)?

**L2 Cache** — это кэш на уровне сессии JPA, который хранит объекты между транзакциями. В отличие от L1 Cache (кэш первого уровня), который существует только в рамках одной транзакции, L2 Cache является общим для всех транзакций.

#### Преимущества L2 Cache:

1. **Снижение нагрузки на БД**: Меньше запросов к базе данных
2. **Улучшение производительности**: Быстрый доступ к часто используемым данным
3. **Масштабируемость**: Возможность распределенного кэширования

#### Почему выбран Infinispan?

**Infinispan** — это распределенная платформа кэширования данных в памяти с открытым исходным кодом. Преимущества:

- **Распределенное кэширование**: Поддержка кластеров
- **Гибкая конфигурация**: Различные стратегии вытеснения и истечения
- **JCache совместимость**: Стандартный API для работы с кэшем
- **Высокая производительность**: Оптимизирован для работы в памяти

#### Стратегии вытеснения (Eviction):

- **LRU (Least Recently Used)**: Удаление наименее используемых элементов
- **LFU (Least Frequently Used)**: Удаление редко используемых элементов
- **FIFO (First In First Out)**: Удаление старейших элементов

#### Политики истечения (Expiration):

- **`lifespan`**: Абсолютное время жизни объекта в кэше
- **`max-idle`**: Время неактивности объекта перед удалением

### 2.2. Реализация

#### 2.2.1. Добавление зависимостей

```xml
<dependency>
    <groupId>org.infinispan</groupId>
    <artifactId>infinispan-jcache</artifactId>
    <version>14.0.18.Final</version>
</dependency>
<dependency>
    <groupId>org.infinispan</groupId>
    <artifactId>infinispan-core</artifactId>
    <version>14.0.18.Final</version>
</dependency>
```

#### 2.2.2. Конфигурация Infinispan

Создан файл `infinispan.xml` с тремя типами кэшей:

1. **default cache**: Базовый кэш для общих целей
2. **entity-cache**: Кэш для сущностей (больший размер, большее время жизни)
3. **query-cache**: Кэш для результатов запросов (меньший размер)

#### 2.2.3. Настройка L2 Cache в persistence.xml

```xml
<property name="eclipselink.cache.shared.default" value="true"/>
<property name="eclipselink.cache.type.default" value="FULL"/>
<property name="eclipselink.cache.size.default" value="1000"/>
<property name="eclipselink.cache.expiry" value="3600000"/>
```

### 2.3. Параметры конфигурации Infinispan

#### 2.3.1. Default Cache

| Параметр | Значение | Влияние на уровень хранения |
|----------|---------|----------------------------|
| `size` | 1000 объектов | Ограничивает количество объектов в памяти. При превышении применяется стратегия вытеснения. |
| `lifespan` | 3600000 мс (1 час) | Объекты автоматически удаляются через 1 час независимо от использования. Обеспечивает актуальность данных. |
| `max-idle` | 1800000 мс (30 мин) | Объекты удаляются, если не используются 30 минут. Освобождает место для более активных данных. |

**Влияние**: Баланс между актуальностью данных и производительностью. Короткое время жизни обеспечивает свежесть данных, но увеличивает нагрузку на БД.

#### 2.3.2. Entity Cache

| Параметр | Значение | Влияние на уровень хранения |
|----------|---------|----------------------------|
| `size` | 2000 объектов | Больше места для сущностей, которые часто используются. |
| `lifespan` | 7200000 мс (2 часа) | Сущности хранятся дольше, так как они реже изменяются. |
| `max-idle` | 3600000 мс (1 час) | Дольше хранятся неактивные сущности, что полезно для справочных данных. |

**Влияние**: Оптимизирован для сущностей, которые редко изменяются, но часто читаются. Уменьшает количество запросов к БД для справочных данных.

#### 2.3.3. Query Cache

| Параметр | Значение | Влияние на уровень хранения |
|----------|---------|----------------------------|
| `size` | 500 объектов | Меньший размер, так как результаты запросов могут быстро устаревать. |
| `lifespan` | 1800000 мс (30 мин) | Короткое время жизни для обеспечения актуальности результатов. |
| `max-idle` | 900000 мс (15 мин) | Быстрое удаление неиспользуемых результатов запросов. |

**Влияние**: Оптимизирован для часто выполняемых запросов с одинаковыми параметрами. Быстрое истечение предотвращает использование устаревших данных.

### 2.4. Логирование статистики L2 Cache

#### 2.4.1. Теоретическая часть

**Cache Statistics** (статистика кэша) включает:
- **Cache Hits**: Успешные обращения к кэшу (данные найдены)
- **Cache Misses**: Неуспешные обращения (данные не найдены, требуется запрос к БД)
- **Hit Rate**: Процент успешных обращений (hits / (hits + misses))

#### 2.4.2. Реализация через CDI Interceptors

Для Jakarta EE приложений используется механизм **CDI Interceptors** (Contexts and Dependency Injection Interceptors).

**Преимущества CDI Interceptors:**
- Декларативный подход через аннотации
- Разделение бизнес-логики и перекрестных задач
- Легкое включение/отключение функциональности

**Реализация:**

1. **Аннотация `@CacheStatisticsLogging`**:
```java
@InterceptorBinding
@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD})
public @interface CacheStatisticsLogging {
}
```

2. **Interceptor `CacheStatisticsInterceptor`**:
```java
@Interceptor
@CacheStatisticsLogging
@Priority(Interceptor.Priority.APPLICATION)
public class CacheStatisticsInterceptor {
    @AroundInvoke
    public Object logCacheStatistics(InvocationContext context) throws Exception {
        // Получение статистики до и после выполнения метода
        // Логирование hits, misses, hit rate
    }
}
```

3. **Регистрация в `beans.xml`**:
```xml
<interceptors>
    <class>com.example.lab1.interceptors.CacheStatisticsInterceptor</class>
</interceptors>
```

4. **Использование**:
```java
@CacheStatisticsLogging
public ImportResult importFromJSON(...) {
    // Метод будет логировать статистику кэша
}
```

#### 2.4.3. Управление логированием

Реализован REST API для включения/отключения логирования:

- `GET /cache-statistics/logging/status` — проверка статуса
- `POST /cache-statistics/logging/enable` — включение
- `POST /cache-statistics/logging/disable` — отключение

Логирование управляется через системное свойство `cache.statistics.logging.enabled`.

## 3. Сохранение файлов в MinIO

### 3.1. Теоретическая часть

#### Что такое MinIO?

**MinIO** — это высокопроизводительное объектное хранилище, совместимое с Amazon S3 API. Это распределенная система хранения объектов, оптимизированная для работы с большими объемами данных.

#### Преимущества MinIO:

1. **S3-совместимость**: Работает с любыми приложениями, поддерживающими S3
2. **Высокая производительность**: Оптимизировано для чтения/записи
3. **Масштабируемость**: Поддержка распределенных кластеров
4. **Простота развертывания**: Легко запускается в Docker

#### Концепции MinIO:

- **Bucket**: Контейнер для объектов (аналог папки)
- **Object**: Файл с данными и метаданными
- **Object Name**: Уникальный идентификатор объекта в bucket

### 3.2. Реализация

#### 3.2.1. Настройка MinIO в docker-compose.yml

```yaml
minio:
  image: minio/minio:latest
  container_name: lab1-minio
  command: server /data --console-address ":9001"
  environment:
    MINIO_ROOT_USER: minioadmin
    MINIO_ROOT_PASSWORD: minioadmin
  ports:
    - "9000:9000"  # API
    - "9001:9001"  # Console
  volumes:
    - miniodata:/data
```

#### 3.2.2. Сервис MinIOService

Реализован класс `MinIOService` с методами:
- `uploadFile()` — загрузка файла
- `downloadFile()` — скачивание файла
- `deleteFile()` — удаление файла (для отката транзакций)
- `isAvailable()` — проверка доступности MinIO

#### 3.2.3. Интеграция с историей импорта

В таблицу `import_history` добавлено поле `file_object_name` для хранения имени файла в MinIO.

#### 3.2.4. Endpoint для скачивания

Реализован REST endpoint `GET /import/file/{historyId}` для скачивания файлов из истории импорта.

## 4. Реализация распределенной транзакции

### 4.1. Теоретическая часть

#### Что такое распределенная транзакция?

**Распределенная транзакция** — это транзакция, которая затрагивает несколько независимых ресурсов (например, БД и файловое хранилище), которые не поддерживают единый механизм транзакций.

#### Проблема распределенных транзакций:

При выполнении операций с несколькими ресурсами необходимо обеспечить **ACID-свойства**:
- **Atomicity (Атомарность)**: Все операции выполняются или ни одна
- **Consistency (Согласованность)**: Система остается в согласованном состоянии
- **Isolation (Изоляция)**: Транзакции не мешают друг другу
- **Durability (Долговечность)**: Изменения сохраняются после завершения

#### Двухфазный коммит (2PC - Two-Phase Commit)

**Двухфазный коммит** — это протокол для обеспечения атомарности распределенных транзакций.

**Фаза 1: PREPARE (Подготовка)**
- Координатор отправляет запрос "prepare" всем участникам
- Каждый участник выполняет операцию, но не фиксирует изменения
- Участник отвечает "готов" или "не готов"

**Фаза 2: COMMIT (Фиксация) или ROLLBACK (Откат)**
- Если все участники готовы → координатор отправляет "commit"
- Если хотя бы один не готов → координатор отправляет "rollback"
- Участники фиксируют или откатывают изменения

**Преимущества 2PC:**
- Гарантирует атомарность
- Обеспечивает согласованность данных

**Недостатки 2PC:**
- Блокировка ресурсов на время транзакции
- Возможность блокировок при сбоях
- Высокая сложность реализации

### 4.2. Реализация

#### 4.2.1. DistributedTransactionManager

Реализован класс `DistributedTransactionManager` с методом `executeDistributedTransaction()`, который:

1. **Фаза PREPARE**:
   - Загружает файл в MinIO (получает `fileObjectName`)
   - Сохраняет данные в БД (в рамках транзакции, но не коммитит)

2. **Фаза COMMIT**:
   - Коммитит транзакцию БД
   - Файл уже зафиксирован в MinIO

3. **Обработка ошибок (ROLLBACK)**:
   - При любой ошибке удаляет файл из MinIO
   - Откатывает транзакцию БД (через `@Transactional`)

#### 4.2.2. Интерфейсы операций

```java
public interface DatabaseOperation<T> {
    T prepare() throws Exception;  // Подготовка операции с БД
    default void commit() throws Exception;  // Коммит (по умолчанию через @Transactional)
}

public interface FileOperation {
    String prepare() throws Exception;  // Загрузка файла в MinIO
}
```

#### 4.2.3. Использование в ImportService

При импорте данных с файлом используется распределенная транзакция:

```java
transactionManager.executeDistributedTransaction(
    // Операция с БД
    () -> {
        // Сохранение объектов в БД
        return saveHistory(history);
    },
    // Операция с файлом
    () -> {
        // Загрузка файла в MinIO
        return minIOService.uploadFile(...);
    }
);
```

### 4.3. Обработка сценариев отказов

#### 4.3.1. Отказ файлового хранилища (БД работает)

**Сценарий**: MinIO недоступен, но БД работает.

**Обработка**:
1. Метод `minIOService.isAvailable()` возвращает `false`
2. Используется простая транзакция только с БД
3. Файл не сохраняется, но данные импортируются успешно

**Код**:
```java
if (finalFileContent == null || !minIOService.isAvailable()) {
    // Простое сохранение в БД без файла
    // ...
}
```

#### 4.3.2. Отказ БД (файловое хранилище работает)

**Сценарий**: БД недоступна, но MinIO работает.

**Обработка**:
1. Файл загружается в MinIO (фаза PREPARE успешна)
2. Ошибка при сохранении в БД
3. Файл удаляется из MinIO (откат)
4. Транзакция БД откатывается через `@Transactional`

**Код**:
```java
try {
    dbResult = dbOperation.prepare();
} catch (Exception e) {
    // Откатываем файловую операцию
    if (fileObjectName != null) {
        minIOService.deleteFile(fileObjectName);
    }
    throw new TransactionException("Database preparation failed", e);
}
```

#### 4.3.3. Ошибка в бизнес-логике

**Сценарий**: И БД, и MinIO работают, но возникает `RuntimeException` в коде.

**Обработка**:
1. Файл загружен в MinIO
2. Данные подготовлены в БД
3. Ошибка в бизнес-логике между операциями
4. Файл удаляется из MinIO
5. Транзакция БД откатывается

**Код**:
```java
catch (Exception e) {
    // Откатываем файловую операцию при любой неожиданной ошибке
    if (fileObjectName != null) {
        minIOService.deleteFile(fileObjectName);
    }
    throw new TransactionException("Unexpected error", e);
}
```

## 5. Обработка параллельных запросов

### 5.1. Теоретическая часть

#### Проблемы параллельных запросов

При одновременной обработке нескольких запросов могут возникнуть:

1. **Race Conditions (Состояние гонки)**: Конкуренция за общие ресурсы
2. **Deadlocks (Взаимные блокировки)**: Две транзакции блокируют друг друга
3. **Lost Updates (Потеря обновлений)**: Перезапись изменений другого запроса
4. **Dirty Reads (Грязное чтение)**: Чтение незафиксированных данных

#### Уровни изоляции транзакций

1. **READ UNCOMMITTED**: Минимальная изоляция, возможны грязные чтения
2. **READ COMMITTED**: Чтение только зафиксированных данных
3. **REPEATABLE READ**: Гарантирует повторяемость чтений
4. **SERIALIZABLE**: Максимальная изоляция, полная сериализация

### 5.2. Реализация

#### 5.2.1. Блокировки на уровне БД

В `persistence.xml` настроен timeout для блокировок:

```xml
<property name="jakarta.persistence.lock.timeout" value="5000"/>
```

Это означает, что при попытке получить блокировку приложение будет ждать максимум 5 секунд, после чего выбросит исключение.

#### 5.2.2. Уникальные имена файлов

Для предотвращения конфликтов при параллельной загрузке файлов используется генерация уникальных имен:

```java
private String generateObjectName(String fileName) {
    return System.currentTimeMillis() + "_" + fileName;
}
```

Использование `System.currentTimeMillis()` гарантирует уникальность имени файла даже при параллельных запросах.

#### 5.2.3. Атомарность операций

Использование `@Transactional` обеспечивает атомарность операций с БД:

```java
@Transactional(rollbackOn = Exception.class)
public ImportResult importFromJSON(...) {
    // Все операции выполняются атомарно
}
```

При ошибке все изменения откатываются автоматически.

### 5.3. Примеры ситуаций при параллельных запросах

#### Ситуация 1: Два пользователя импортируют одинаковые данные одновременно

**Сценарий**:
- Пользователь A и пользователь B одновременно импортируют файл с одинаковыми данными
- Оба запроса пытаются создать одни и те же сущности

**Обработка**:
1. Каждый запрос выполняется в отдельной транзакции (`@Transactional`)
2. При попытке создать дубликат возникает исключение уникальности
3. Один запрос успешно завершается, второй получает ошибку валидации
4. Файлы в MinIO имеют разные имена (благодаря `System.currentTimeMillis()`)

**Результат**: Данные не дублируются, каждый запрос обрабатывается независимо.

#### Ситуация 2: Параллельное чтение и обновление одной сущности

**Сценарий**:
- Пользователь A читает сущность `BookCreature` с id=1
- Пользователь B одновременно обновляет ту же сущность
- Пользователь A снова читает сущность

**Обработка**:
1. L2 Cache хранит кэшированную версию сущности
2. При обновлении сущности кэш инвалидируется
3. При следующем чтении данные загружаются из БД (cache miss)
4. Уровень изоляции `READ COMMITTED` гарантирует чтение актуальных данных

**Результат**: Пользователь A видит обновленные данные после коммита транзакции пользователя B.

#### Ситуация 3: Параллельная загрузка файлов с одинаковыми именами

**Сценарий**:
- Два пользователя одновременно загружают файл с именем `import.json`

**Обработка**:
1. Каждый запрос генерирует уникальное имя: `1234567890_import.json` и `1234567891_import.json`
2. Файлы сохраняются в MinIO с разными именами
3. В БД сохраняются разные `file_object_name` для каждой истории импорта

**Результат**: Оба файла успешно сохраняются без конфликтов.

#### Ситуация 4: Блокировка при одновременном обновлении

**Сценарий**:
- Пользователь A начинает обновление сущности `MagicCity` с id=1
- Пользователь B одновременно пытается обновить ту же сущность

**Обработка**:
1. Первая транзакция получает блокировку на строку
2. Вторая транзакция ждет освобождения блокировки (до 5 секунд)
3. Если первая транзакция завершается быстро → вторая получает блокировку
4. Если первая транзакция долгая → вторая получает `LockTimeoutException`

**Результат**: Изменения применяются последовательно, предотвращая потерю данных.

#### Ситуация 5: Откат одной транзакции при успешной другой

**Сценарий**:
- Пользователь A импортирует данные (файл + БД)
- Пользователь B одновременно импортирует данные
- Транзакция пользователя A откатывается из-за ошибки валидации
- Транзакция пользователя B успешно завершается

**Обработка**:
1. Транзакция A: файл загружен в MinIO, данные подготовлены в БД
2. Ошибка валидации → файл удаляется из MinIO, транзакция БД откатывается
3. Транзакция B: выполняется независимо, успешно завершается

**Результат**: Изоляция транзакций гарантирует, что откат одной не влияет на другую.

### 5.4. JMeter тестирование

Для проверки корректности работы при параллельных запросах используется Apache JMeter с тест-планом `jmeter-test-plan.jmx`.

**Сценарий тестирования**:
- Несколько потоков одновременно отправляют запросы на импорт
- Проверяется отсутствие ошибок и конфликтов
- Проверяется корректность сохранения данных и файлов
