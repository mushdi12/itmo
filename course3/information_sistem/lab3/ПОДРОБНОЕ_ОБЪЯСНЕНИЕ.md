Представь, что у тебя есть веб-приложение (как сайт), которое:

## Часть 1: Connection Pool (Пул соединений) - Зачем и как?

### 1.1. Проблема без Connection Pool

**Представь ситуацию:**
- У тебя есть магазин (приложение)
- Каждый покупатель (запрос к БД) должен сам построить дорогу к складу (создать соединение с БД)
- После покупки дорогу разрушают (закрывают соединение)
- Следующий покупатель снова строит дорогу с нуля

**Проблемы:**
- Очень медленно (каждый раз строить дорогу)
- Много ресурсов тратится впустую
- При большом количестве покупателей - хаос

### 1.2. Решение: Connection Pool

**Теперь представь:**
- Есть готовый автобусный маршрут (пул соединений)
- Автобусы (соединения) постоянно ездят туда-сюда
- Покупатель садится в автобус, едет, делает покупку, выходит
- Автобус возвращается и ждет следующего покупателя

**Преимущества:**
- Быстро (не нужно строить дорогу каждый раз)
- Эффективно (автобусы переиспользуются)
- Контролируемо (ограниченное количество автобусов)

### 1.3. Что такое Druid?

**Druid** - это специальная система управления автобусами (соединениями к БД).

**Почему именно Druid?**
1. **Мониторинг**: Видно, сколько автобусов занято, сколько свободно
2. **Защита**: Есть защита от "взлома" (SQL-инъекции)
3. **Производительность**: Очень быстрый
4. **Гибкость**: Можно настроить под любые нужды

### 1.4. Как я это реализовал?

#### Шаг 1: Добавил библиотеку Druid

В файле `pom.xml` (это список всех библиотек, которые использует проект):

```xml
<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>druid</artifactId>
    <version>1.2.20</version>
</dependency>
```

**Что это значит?** Говорю Maven (системе сборки): "Скачай и подключи библиотеку Druid версии 1.2.20"

#### Шаг 2: Создал класс для управления пулом

Создал файл `DruidDataSourceProvider.java`:

```java
@ApplicationScoped  // Этот объект создается один раз при старте приложения
public class DruidDataSourceProvider {
    private DruidDataSource dataSource;  // Это и есть наш "автобусный парк"
    
    @PostConstruct  // Этот метод выполняется при создании объекта
    public void init() {
        // Создаю новый "автобусный парк"
        dataSource = new DruidDataSource();
        
        // Настраиваю, куда ездить (адрес базы данных)
        dataSource.setUrl("jdbc:postgresql://localhost:5433/studs");
        dataSource.setUsername("postgres");
        dataSource.setPassword("postgres");
        
        // НАСТРОЙКИ ПУЛА (это самое важное):
        
        // Сколько автобусов сразу готово при старте
        dataSource.setInitialSize(5);
        
        // Минимум автобусов, которые всегда должны быть готовы
        dataSource.setMinIdle(5);
        
        // Максимум автобусов одновременно
        dataSource.setMaxActive(20);
        
        // Сколько ждать свободный автобус (60 секунд)
        dataSource.setMaxWait(60000);
        
        // Как часто проверять, не сломались ли автобусы
        dataSource.setTimeBetweenEvictionRunsMillis(60000);
        
        // Если автобус простаивает 5 минут - убрать его
        dataSource.setMinEvictableIdleTimeMillis(300000);
        
        // Команда для проверки: "Автобус, ты еще работает?"
        dataSource.setValidationQuery("SELECT 1");
        
        // Проверять автобусы, пока они стоят на стоянке
        dataSource.setTestWhileIdle(true);
        
        // Кэшировать часто используемые маршруты (запросы)
        dataSource.setPoolPreparedStatements(true);
        
        // Защита от взлома и статистика
        dataSource.setFilters("stat,wall");
    }
}
```

**Простыми словами:**
- Создаю "автобусный парк" (пул соединений)
- Настраиваю, сколько автобусов минимум, максимум
- Настраиваю, как проверять, что автобусы работают
- Включаю защиту и статистику

#### Шаг 3: Параметры и их влияние

**`initialSize = 5`**
- При старте приложения сразу создается 5 соединений
- **Зачем?** Чтобы первые запросы были быстрыми (не нужно ждать создания соединения)
- **Минус?** Больше потребление памяти

**`minIdle = 5`**
- Всегда должно быть минимум 5 свободных соединений
- **Зачем?** Чтобы при внезапной нагрузке не нужно было создавать соединения
- **Аналогия:** Всегда 5 автобусов на стоянке, даже если нет пассажиров

**`maxActive = 20`**
- Максимум 20 соединений одновременно
- **Зачем?** Чтобы не перегрузить базу данных
- **Аналогия:** Не больше 20 автобусов на дороге одновременно

**`maxWait = 60000` (60 секунд)**
- Если все автобусы заняты, ждать максимум 60 секунд
- **Зачем?** Чтобы запрос не висел бесконечно
- **Что происходит?** Если за 60 секунд автобус не освободился - ошибка

**`testWhileIdle = true`**
- Проверять автобусы, пока они стоят на стоянке
- **Зачем?** Чтобы не дать сломанный автобус пассажиру
- **Аналогия:** Механик проверяет автобусы на стоянке

## Часть 2: L2 Cache (Кэш второго уровня) - Зачем и как?

### 2.1. Проблема без кэша

**Представь ситуацию:**
- Ты библиотекарь в большой библиотеке
- Каждый раз, когда кто-то спрашивает "Где книга X?", ты бежишь в хранилище (БД)
- Даже если эту же книгу только что спрашивали 5 минут назад
- Ты снова бежишь в хранилище

**Проблемы:**
- Медленно (каждый раз идти в хранилище)
- Нагрузка на хранилище (БД)
- Если 100 человек спрашивают одну книгу - ты 100 раз бежишь в хранилище

### 2.2. Решение: Кэш

**Теперь представь:**
- У тебя есть стол рядом (кэш в памяти)
- На столе лежат 10 самых популярных книг
- Когда спрашивают книгу - сначала проверяешь стол
- Если книга на столе - даешь сразу (быстро!)
- Если нет - идешь в хранилище и кладешь на стол

**Преимущества:**
- Очень быстро для популярных книг
- Меньше нагрузки на хранилище
- Если 100 человек спрашивают одну книгу - ты идешь в хранилище только 1 раз

### 2.3. Что такое L1 и L2 Cache?

**L1 Cache (кэш первого уровня):**
- Это твой личный стол (только для одной транзакции)
- Когда транзакция заканчивается - стол очищается
- **Аналогия:** Ты работаешь с клиентом, держишь его книги на столе, после работы убираешь

**L2 Cache (кэш второго уровня):**
- Это общий стол для всех (для всех транзакций)
- Книги остаются на столе даже после окончания транзакции
- **Аналогия:** Общий стол в библиотеке, где лежат популярные книги для всех

### 2.4. Что такое Infinispan?

**Infinispan** - это система управления общим столом (кэшем).

**Почему Infinispan?**
1. **Распределенный**: Можно иметь несколько столов в разных местах
2. **Гибкий**: Можно настроить, сколько книг, как долго хранить
3. **Быстрый**: Оптимизирован для работы в памяти
4. **Стандартный**: Использует стандартный API (JCache)

### 2.5. Как я это реализовал?

#### Шаг 2: Создал конфигурацию кэша

Создал файл `infinispan.xml`:

```xml
<cache-container name="jpa-cache-container">
    <!-- Обычный кэш (для всего подряд) -->
    <local-cache name="default">
        <memory>
            <object size="1000"/>  <!-- Максимум 1000 объектов -->
        </memory>
        <expiration 
            lifespan="3600000"      <!-- Живет 1 час -->
            max-idle="1800000"/>    <!-- Если не используется 30 мин - удалить -->
    </local-cache>
    
    <!-- Кэш для сущностей (книги, города и т.д.) -->
    <local-cache name="entity-cache">
        <memory>
            <object size="2000"/>  <!-- Больше места для сущностей -->
        </memory>
        <expiration 
            lifespan="7200000"      <!-- Живет 2 часа (сущности редко меняются) -->
            max-idle="3600000"/>   <!-- Если не используется 1 час - удалить -->
    </local-cache>
    
    <!-- Кэш для результатов запросов -->
    <local-cache name="query-cache">
        <memory>
            <object size="500"/>   <!-- Меньше места (запросы быстро устаревают) -->
        </memory>
        <expiration 
            lifespan="1800000"      <!-- Живет 30 минут -->
            max-idle="900000"/>    <!-- Если не используется 15 мин - удалить -->
    </local-cache>
</cache-container>
```

**Простыми словами:**
- У меня 3 стола (кэша):
  1. **Обычный стол**: 1000 книг, хранятся 1 час
  2. **Стол для справочников**: 2000 книг, хранятся 2 часа (они редко меняются)
  3. **Стол для запросов**: 500 результатов, хранятся 30 минут (быстро устаревают)

### 2.6. Логирование статистики кэша

#### Зачем нужно логирование?

**Проблема:** Как узнать, работает ли кэш хорошо?
- Сколько раз данные нашли в кэше (hits - попадания)?
- Сколько раз не нашли и пришлось идти в БД (misses - промахи)?
- Какой процент попаданий (hit rate)?

**Решение:** Логировать статистику после каждого метода

#### Как работает CDI Interceptor?

**Интерцептор** - это как "перехватчик" вызовов методов.

**Аналогия:**
- Ты вызываешь метод `importFromJSON()`
- Но перед вызовом срабатывает "перехватчик"
- Он записывает статистику кэша ДО выполнения
- Метод выполняется
- После выполнения "перехватчик" снова записывает статистику
- Вычисляет разницу и логирует

#### Реализация:

**Шаг 1: Создал аннотацию**

Файл `CacheStatisticsLogging.java`:

```java
@InterceptorBinding  // Это аннотация для интерцептора
@Retention(RetentionPolicy.RUNTIME)  // Действует во время выполнения
@Target({ElementType.TYPE, ElementType.METHOD})  // Можно ставить на класс или метод
public @interface CacheStatisticsLogging {
    // Это просто маркер - говорит "здесь нужно логировать статистику"
}
```

**Шаг 2: Создал интерцептор**

Файл `CacheStatisticsInterceptor.java`:

```java
@Interceptor  // Это интерцептор
@CacheStatisticsLogging  // Срабатывает на методах с этой аннотацией
@Priority(Interceptor.Priority.APPLICATION)  // Приоритет выполнения
public class CacheStatisticsInterceptor {
    
    @AroundInvoke  // Выполняется ВОКРУГ вызова метода (до и после)
    public Object logCacheStatistics(InvocationContext context) throws Exception {
        // Проверяю, включено ли логирование
        if (!isCacheLoggingEnabled()) {
            return context.proceed();  // Если выключено - просто выполняю метод
        }
        
        // Получаю статистику ДО выполнения метода
        CacheStatistics beforeStats = getCacheStatistics();
        
        // ВЫПОЛНЯЮ МЕТОД (это и есть context.proceed())
        Object result = context.proceed();
        
        // Получаю статистику ПОСЛЕ выполнения метода
        CacheStatistics afterStats = getCacheStatistics();
        
        // Вычисляю разницу
        long hitsDiff = afterStats.hits - beforeStats.hits;      // Сколько попаданий
        long missesDiff = afterStats.misses - beforeStats.misses; // Сколько промахов
        
        // Логирую
        logger.info(String.format(
            "L2 Cache Statistics for %s.%s: Hits: %d, Misses: %d, Hit Rate: %.2f%%",
            context.getMethod().getDeclaringClass().getSimpleName(),  // Имя класса
            context.getMethod().getName(),                            // Имя метода
            hitsDiff,                                                 // Попадания
            missesDiff,                                               // Промахи
            (hitsDiff + missesDiff) > 0 ? 
                (hitsDiff * 100.0 / (hitsDiff + missesDiff)) : 0.0  // Процент попаданий
        ));
        
        return result;  // Возвращаю результат метода
    }
}
```

**Простыми словами:**
1. Метод помечен аннотацией `@CacheStatisticsLogging`
2. Перед вызовом записываю статистику кэша
3. Выполняю метод
4. После вызова снова записываю статистику
5. Вычисляю разницу и логирую

**Шаг 3: Зарегистрировал интерцептор**

В файле `beans.xml`:

```xml
<interceptors>
    <class>com.example.lab1.interceptors.CacheStatisticsInterceptor</class>
</interceptors>
```

**Что это значит?** Говорю CDI: "Вот интерцептор, используй его"

**Шаг 4: Использование**

В `ImportService.java`:

```java
@CacheStatisticsLogging  // Ставлю аннотацию на метод
public ImportResult importFromJSON(...) {
    // Этот метод будет логировать статистику кэша
}
```

#### Управление логированием

Создал REST API для включения/отключения:

```java
@Path("/cache-statistics")
public class CacheStatisticsResource {
    
    @GET
    @Path("/logging/status")
    public Response getLoggingStatus() {
        // Проверяю, включено ли логирование
        boolean enabled = CacheStatisticsConfig.isLoggingEnabled();
        return Response.ok(Map.of("enabled", enabled)).build();
    }
    
    @POST
    @Path("/logging/enable")
    public Response enableLogging() {
        // Включаю логирование
        CacheStatisticsConfig.enableLogging();
        return Response.ok(Map.of("success", true)).build();
    }
    
    @POST
    @Path("/logging/disable")
    public Response disableLogging() {
        // Выключаю логирование
        CacheStatisticsConfig.disableLogging();
        return Response.ok(Map.of("success", true)).build();
    }
}
```

**Как использовать:**
- `GET http://localhost:8080/cache-statistics/logging/status` - проверить статус
- `POST http://localhost:8080/cache-statistics/logging/enable` - включить
- `POST http://localhost:8080/cache-statistics/logging/disable` - выключить

## Часть 3: MinIO (Файловое хранилище) - Зачем и как?

### 3.1. Проблема без файлового хранилища

**Представь ситуацию:**
- Пользователи загружают файлы для импорта данных
- Файлы хранятся на сервере приложения
- Проблемы:
  - Если сервер упадет - файлы потеряются
  - Если нужно масштабировать (несколько серверов) - файлы не синхронизируются
  - База данных перегружается (хранить файлы в БД неэффективно)

### 3.2. Решение: MinIO

**MinIO** - это как "облачное хранилище" (как Google Drive или Dropbox), но:
- Работает локально (на твоем сервере)
- Совместимо с Amazon S3 (стандарт индустрии)
- Очень быстрое
- Легко масштабируется

**Аналогия:**
- Вместо того, чтобы хранить книги в кабинете (на сервере приложения)
- Хранишь их в специальном хранилище (MinIO)
- Хранилище специализируется только на хранении
- Приложение может работать на нескольких серверах, но файлы в одном месте

### 3.3. Как я это реализовал?

#### Шаг 1: Настроил MinIO в Docker

В файле `docker-compose.yml`:

```yaml
minio:
  image: minio/minio:latest  # Использую официальный образ MinIO
  container_name: lab1-minio
  command: server /data --console-address ":9001"  # Запускаю сервер
  environment:
    MINIO_ROOT_USER: minioadmin      # Логин администратора
    MINIO_ROOT_PASSWORD: minioadmin  # Пароль администратора
  ports:
    - "9000:9000"  # Порт для API (загрузка/скачивание файлов)
    - "9001:9001"  # Порт для веб-консоли (управление через браузер)
  volumes:
    - miniodata:/data  # Где хранить файлы (на диске)
```

**Что это значит?**
- Запускаю MinIO в Docker контейнере
- Доступен на порту 9000 (API) и 9001 (веб-интерфейс)
- Файлы хранятся в томе `miniodata`

**Как запустить:**
```bash
docker-compose up -d  # Запускает MinIO в фоне
```

#### Шаг 2: Создал сервис для работы с MinIO

Файл `MinIOService.java`:

```java
@ApplicationScoped  // Один экземпляр на все приложение
public class MinIOService {
    private static final String BUCKET_NAME = "import-files";  // Название "папки"
    private MinioClient minioClient;  // Клиент для работы с MinIO
    private boolean initialized = false;
    
    @PostConstruct  // Выполняется при старте приложения
    public void init() {
        try {
            // Создаю клиент для подключения к MinIO
            minioClient = MinioClient.builder()
                    .endpoint("http://localhost:9000")  // Адрес MinIO
                    .credentials("minioadmin", "minioadmin")  // Логин и пароль
                    .build();
            
            // Проверяю, существует ли "папка" (bucket)
            boolean found = minioClient.bucketExists(
                BucketExistsArgs.builder()
                    .bucket(BUCKET_NAME)
                    .build()
            );
            
            // Если не существует - создаю
            if (!found) {
                minioClient.makeBucket(
                    MakeBucketArgs.builder()
                        .bucket(BUCKET_NAME)
                        .build()
                );
            }
            
            initialized = true;  // Все готово
        } catch (Exception e) {
            initialized = false;  // Ошибка при инициализации
        }
    }
    
    // Метод для загрузки файла
    public String uploadFile(InputStream inputStream, String fileName, 
                            String contentType, long size) {
        // Генерирую уникальное имя файла
        String objectName = generateObjectName(fileName);
        
        // Загружаю файл в MinIO
        minioClient.putObject(
            PutObjectArgs.builder()
                .bucket(BUCKET_NAME)           // В какую "папку"
                .object(objectName)             // Имя файла
                .stream(inputStream, size, -1) // Данные файла
                .contentType(contentType)       // Тип файла (application/json)
                .build()
        );
        
        return objectName;  // Возвращаю имя файла в MinIO
    }
    
    // Метод для скачивания файла
    public InputStream downloadFile(String objectName) {
        return minioClient.getObject(
            GetObjectArgs.builder()
                .bucket(BUCKET_NAME)
                .object(objectName)
                .build()
        );
    }
    
    // Метод для удаления файла (нужен для отката транзакций)
    public void deleteFile(String objectName) {
        minioClient.removeObject(
            RemoveObjectArgs.builder()
                .bucket(BUCKET_NAME)
                .object(objectName)
                .build()
        );
    }
    
    // Генерирую уникальное имя файла
    private String generateObjectName(String fileName) {

        // Пример: "1703123456789_import.json"
    }
}
```

**Простыми словами:**

## Часть 4: Распределенная транзакция (Двухфазный коммит) - Самое сложное!

### 4.1. Проблема: Атомарность операций

**Представь ситуацию:**
- Пользователь загружает файл и импортирует данные
- Нужно:
  1. Сохранить файл в MinIO
  2. Сохранить данные в БД
  3. Сохранить запись в истории импорта

**Проблема:** Что если:
- Файл сохранился в MinIO ✅
- Но ошибка при сохранении в БД ❌
- Файл остался в MinIO, но данных нет в БД
- **Результат:** Несогласованность данных!

**Нужно:** Либо все успешно, либо ничего не сохраняется

### 4.2. Что такое транзакция?

**Транзакция** - это группа операций, которые должны выполниться либо все, либо ни одна.

**Свойства транзакций (ACID):**
- **A**tomicity (Атомарность): Все или ничего
- **C**onsistency (Согласованность): Данные остаются согласованными
- **I**solation (Изоляция): Транзакции не мешают друг другу
- **D**urability (Долговечность): После завершения изменения сохраняются

**Проблема:** БД поддерживает транзакции, но MinIO - нет!

### 4.3. Решение: Двухфазный коммит (2PC)

**Двухфазный коммит** - это протокол для обеспечения атомарности операций с несколькими системами.

**Аналогия с покупкой:**
1. **Фаза 1 (PREPARE - Подготовка):**
   - Ты: "Я хочу купить это и это"
   - Продавец: "Хорошо, я подготовил товары, но еще не продал"
   - Банк: "Хорошо, я зарезервировал деньги, но еще не списал"

2. **Фаза 2 (COMMIT - Фиксация):**
   - Если все готовы:
     - Ты: "Покупаю!"
     - Продавец: "Продано!"
     - Банк: "Деньги списаны!"
   - Если что-то не так:
     - Все откатывается (товары возвращаются, деньги не списываются)

### 4.4. Как я это реализовал?

#### Шаг 1: Создал DistributedTransactionManager

Файл `DistributedTransactionManager.java`:

```java
@ApplicationScoped
public class DistributedTransactionManager {
    
    @Inject
    private MinIOService minIOService;  // Сервис для работы с MinIO
    
    @PersistenceContext
    private EntityManager em;  // Для работы с БД
    
    // Главный метод для выполнения распределенной транзакции
    public <T> T executeDistributedTransaction(
            DatabaseOperation<T> dbOperation,    // Операция с БД
            FileOperation fileOperation)         // Операция с файлом
            throws Exception {
        
        Phase phase = Phase.INITIAL;  // Текущая фаза
        String fileObjectName = null;  // Имя файла в MinIO
        T dbResult = null;
        
        try {
            // ========== ФАЗА 1: PREPARE (Подготовка) ==========
            phase = Phase.PREPARE;
            logger.info("Phase 1: PREPARE - Starting distributed transaction");
            
            // 1.1 Подготовка файла (загрузка в MinIO)
            if (fileOperation != null && minIOService.isAvailable()) {
                try {
                    // Загружаю файл в MinIO
                    fileObjectName = fileOperation.prepare();
                    logger.info("Phase 1: File prepared in MinIO: " + fileObjectName);
                } catch (Exception e) {
                    // Если ошибка при загрузке файла - сразу откатываю
                    logger.severe("Phase 1: Failed to prepare file operation");
                    throw new TransactionException("File preparation failed", e);
                }
            }
            
            // 1.2 Подготовка операции с БД
            try {
                // Сохраняю данные в БД (но еще не коммичу!)
                dbResult = dbOperation.prepare();
                logger.info("Phase 1: Database operation prepared");
            } catch (Exception e) {
                // Если ошибка при сохранении в БД - откатываю файл
                logger.severe("Phase 1: Failed to prepare database operation");
                if (fileObjectName != null) {
                    // УДАЛЯЮ файл из MinIO (откат)
                    minIOService.deleteFile(fileObjectName);
                }
                throw new TransactionException("Database preparation failed", e);
            }
            
            // ========== ФАЗА 2: COMMIT (Фиксация) ==========
            phase = Phase.COMMIT;
            logger.info("Phase 2: COMMIT - Committing distributed transaction");
            
            // 2.1 Коммит БД
            try {
                // Коммичу транзакцию БД (данные сохраняются)
                dbOperation.commit();
                logger.info("Phase 2: Database operation committed");
            } catch (Exception e) {
                // Если ошибка при коммите БД - откатываю файл
                logger.severe("Phase 2: Failed to commit database operation");
                if (fileObjectName != null) {
                    // УДАЛЯЮ файл из MinIO (откат)
                    minIOService.deleteFile(fileObjectName);
                }
                throw new TransactionException("Database commit failed", e);
            }
            
            // 2.2 Файл уже зафиксирован в MinIO (MinIO не поддерживает транзакции)
            // Но если была ошибка выше - файл уже удален
            logger.info("Phase 2: File operation committed: " + fileObjectName);
            
            return dbResult;  // Все успешно!
            
        } catch (TransactionException e) {
            // Обработка ошибок транзакции
            logger.severe("Distributed transaction failed in phase: " + phase);
            throw e;
        } catch (Exception e) {
            // Любая неожиданная ошибка
            logger.severe("Unexpected error in distributed transaction");
            // Откатываю файл при любой ошибке
            if (fileObjectName != null) {
                minIOService.deleteFile(fileObjectName);
            }
            throw new TransactionException("Unexpected error", e);
        }
    }
    
    // Интерфейс для операции с БД
    public interface DatabaseOperation<T> {
        T prepare() throws Exception;  // Подготовка (сохранение, но не коммит)
        default void commit() throws Exception {
            // По умолчанию коммит через @Transactional
        }
    }
    
    // Интерфейс для операции с файлом
    public interface FileOperation {
        String prepare() throws Exception;  // Загрузка файла в MinIO
    }
}
```

**Простыми словами:**
1. **Фаза 1 (PREPARE):**
   - Загружаю файл в MinIO
   - Сохраняю данные в БД (но не коммичу)
   - Если ошибка на любом этапе - откатываю все

2. **Фаза 2 (COMMIT):**
   - Коммичу транзакцию БД
   - Файл уже в MinIO
   - Если ошибка - удаляю файл из MinIO

3. **Обработка ошибок:**
   - При любой ошибке удаляю файл из MinIO
   - Транзакция БД откатывается автоматически

#### Шаг 2: Использование в ImportService

В `ImportService.java`:

        ImportHistory savedHistory = transactionManager.executeDistributedTransaction(
            
            // ОПЕРАЦИЯ С БД
            new DistributedTransactionManager.DatabaseOperation<ImportHistory>() {

                public ImportHistory prepare() throws Exception {
                    // Сохраняю все объекты в БД
                    for (BookCreature creature : creatures) {

                    }

                    history.setFileObjectName(fileObjectNameHolder[0]);  // Имя файла

                    ByteArrayInputStream bais = new ByteArrayInputStream(fileContent);

    }
}

2. Передаю их в `executeDistributedTransaction`

## Часть 5: Параллельные запросы

### 5.1. Проблема параллельных запросов

**Представь ситуацию:**
- 10 пользователей одновременно импортируют данные
- Все пытаются сохранить данные в БД
- Все пытаются загрузить файлы в MinIO

**Проблемы:**
1. **Конфликты**: Два пользователя пытаются создать одинаковые данные
2. **Блокировки**: Один пользователь блокирует другого
3. **Потеря данных**: Изменения одного пользователя перезаписываются другим

### 5.2. Как я это решил?

#### Решение 1: Транзакции и изоляция

В `persistence.xml`:

```xml
<property name="jakarta.persistence.lock.timeout" value="5000"/>
```

**Что это значит?**
- Если один пользователь блокирует данные, другой ждет максимум 5 секунд
- Если за 5 секунд блокировка не освободилась - ошибка
- Это предотвращает бесконечные ожидания

**Аналогия:**
- Пользователь A редактирует книгу (блокирует)
- Пользователь B пытается редактировать ту же книгу
- Пользователь B ждет 5 секунд
- Если пользователь A не закончил - пользователь B получает ошибку

#### Решение 2: Уникальные имена файлов

В `MinIOService.java`:

```java
private String generateObjectName(String fileName) {
    return System.currentTimeMillis() + "_" + fileName;
}
```

**Что это значит?**
- Использую текущее время в миллисекундах
- Даже если два пользователя загружают файл одновременно - имена разные
- Пример: `1703123456789_import.json` и `1703123456790_import.json`

**Зачем?** Чтобы не было конфликтов при параллельной загрузке

#### Решение 3: Атомарность операций

Использование `@Transactional`:

```java
@Transactional(rollbackOn = Exception.class)
public ImportResult importFromJSON(...) {
    // Все операции выполняются атомарно
}
```

**Что это значит?**
- Либо все операции успешны, либо все откатываются
- Другие пользователи не видят частично выполненные операции

### 5.3. Примеры ситуаций

#### Ситуация 1: Два пользователя импортируют одинаковые данные

**Сценарий:**
- Пользователь A и B одновременно импортируют файл с одинаковыми данными
- Оба пытаются создать сущность `BookCreature` с одинаковыми полями

**Что происходит:**
1. Каждый запрос выполняется в отдельной транзакции
2. Первая транзакция успешно создает данные
3. Вторая транзакция пытается создать дубликат
4. БД выбрасывает ошибку уникальности
5. Вторая транзакция откатывается

**Результат:** Данные не дублируются, каждый запрос обрабатывается независимо

#### Ситуация 2: Параллельное чтение и обновление

**Сценарий:**
- Пользователь A читает `BookCreature` с id=1
- Пользователь B одновременно обновляет ту же сущность
- Пользователь A снова читает

**Что происходит:**
1. Пользователь A читает из кэша (быстро)
2. Пользователь B обновляет в БД и инвалидирует кэш
3. Пользователь A снова читает - данные загружаются из БД (актуальные)

**Результат:** Пользователь A видит обновленные данные

#### Ситуация 3: Параллельная загрузка файлов

**Сценарий:**
- Два пользователя одновременно загружают файл `import.json`

**Что происходит:**
1. Каждый получает уникальное имя: `1234567890_import.json` и `1234567891_import.json`
2. Файлы сохраняются в MinIO с разными именами
3. В БД сохраняются разные `file_object_name`

**Результат:** Оба файла успешно сохраняются без конфликтов
